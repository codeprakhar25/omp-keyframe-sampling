Reproducing the banked OMP k=8 / 600s arm on AWS gave **.6456 vs the banked .6311**.

Same items, same picks, 98.1% agreement -> numeric drift (torch 2.6.0+cu124 here),
NOT different data. But the drift (+1.45pt) exceeds Table 1's margins
(+0.97 / -0.29 / +0.58), so Modal-banked numbers must NOT be mixed with AWS
numbers in one table. Hence the full 6x2 matrix in one environment.

## Arm plan — SINGLE INSTANCE (decided 2026-08-29 ~07:50Z)
All 11 arms run on `i-0a5066e906b575cf0` alone. k8_omp is already done (it was
the gate): **.6456, n=412**. ~70 min per k=32 arm, ~31 min per k=8 arm ->
finishes ~16:20Z, ~$16.

Parallelising was attempted and abandoned, on purpose:
- A second **g6e.xlarge** is *not* blocked by quota (8 vCPU granted, 4 in use).
  It is blocked by `InsufficientInstanceCapacity` in all four AZs that offer the
  type -- AWS inventory, not our account. A transient `VcpuLimitExceeded` seen
  once was only a terminating instance still holding its 4 vCPU for ~45s.
- A **g5.xlarge** (A10G) was launched to test whether it could take the k=8 half,
  then terminated on the user's instruction: only g6e.xlarge, or nothing. This is
  the right call -- the environment gate above shows a *software* change alone
  moved the number +1.45pt, so mixing GPU architectures inside one table is not
  defensible. Do not reintroduce mixed hardware for these arms.
- `.done` skip markers must stay CLEARED unless a second box is confirmed running
  those arms. Leaving them set makes the runner silently skip arms and finish
  looking successful -- fail-silent, the 2026-07-19 failure mode.

AMI `ami-0e2ba7d97141f4cde` is reusable for R9/R11/R12: ~2 min to launch once
g6e capacity exists, versus the ~1h this environment took to build.
